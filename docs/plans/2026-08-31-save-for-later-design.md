# Save for Later Design

> **Product name: Folio** (renamed 2026-09-03). Memory is what Phi remembers about you, Folio is what you chose to keep. User-facing strings, string keys, and the default folder (`~/Documents/PhiFolio`) carry the new name; internal identifiers (`SaveForLaterService`, `saveForLater.*` bridge types, the Mirage `save-for-later` module, the PostHog flag) keep the working name.

Date: 2026-08-31
Status: draft
Branch: `feat/save-for-later` (proposed)

## Problem

Phi has no way to keep a page. Bookmarks keep a URL, which rots; the reader's
export saves one file, by hand, wherever the save panel was pointed last. There
is no single action that captures a page into a durable, browsable local
collection.

Save for Later is that action. One trigger writes the page into a user-chosen
local folder in two forms:

1. **A markdown version** — the article as text, produced by the same
   extraction ladder Reader View uses, so the markdown quality is the reader
   quality. Portable, greppable, and directly usable as an Obsidian/Logseq
   vault or as agent context.
2. **A webpage version** — the live page as a single self-contained MHTML
   file, byte-faithful, for when the distillation dropped something that
   mattered or the original goes offline.

When the page is a video (YouTube), a text extraction of the DOM is
worthless. Instead the markdown version is an **article generated by
video-gist** — the existing phi-ai capability that turns a video into prose
with timestamp deep links — headed by a link back to the original video.

## Product Decisions

- The library **is the folder**. No database, no in-browser list in v1. The
  markdown files carry YAML frontmatter (title, source URL, saved date, site,
  type), so Finder, Spotlight, Obsidian, and grep are the browsing UI. A
  native library view can be layered on later by reading the folder.
- Each save writes a **flat pair with a shared basename**:
  `2026-08-31 How to Do Great Work.md` and `… .mhtml`, side by side. Flat
  files are what vault tools expect; a folder-per-item layout is rejected
  because it buries the markdown one level down and adds nothing until we
  store per-item assets (we don't — see below).
- The markdown references images by their **absolute origin URLs** (the
  extraction ladder already absolutizes them). The MHTML is the offline-complete
  copy; the markdown is the portable one. We do not mirror image assets to
  disk in v1.
- **MHTML is unconditional, markdown is best-effort.** A save never fails
  outright because extraction refused: the ladder falls back to the
  accessibility-tree rung, and if that also refuses, the markdown is written
  as a stub (frontmatter + link + a "no article detected" note). The user
  always gets a durable copy.
- For videos we capture the watch page's MHTML too — cheap, consistent, and
  it preserves the description/comments state. We **never download the video
  file itself**.
- **No Chromium framework change in v1.** Both capture paths already exist:
  MHTML via the app's CDP session, articles via the Mirage extension
  messaging channel. The reader migration's rule that no article payload
  crosses the Chromium bridge is preserved. The one framework touch — a
  "Save for Later" entry in the page context menu — is deferred to a later
  phase because it requires a bridge method and a framework rebuild.
- **A save is a background job, detached from the tab.** Both capture legs
  start the moment the save is triggered; once their payloads are in hand,
  nothing else needs the page, so closing the tab or navigating away
  mid-save does not lose the save. If the tab dies before a leg finishes
  capturing, that leg degrades per the failure matrix instead of failing
  the job.
- **Disabled in Guest Mode.** A guest session must not write into the
  permanent library; the menu item is disabled and auto-triggers are not
  armed in guest windows.
- Availability degrades with capability, it does not gate the feature:
  - Article extraction requires the Mirage extension (same dependency Reader
    View has today); the AX-tree rung remains as the extension-less fallback.
  - Video-gist requires a signed-in user (it is a backend AI call). Signed
    out or AI off, a video save still writes MHTML plus a stub markdown with
    the link.

## Architecture Overview

A new `SaveForLaterService` in `Sources/States/` orchestrates a save. It is a
`@MainActor` enum of static entry points in the mold of
`ReaderExportService` — stateless policy, no new state container. Per-tab
in-flight status (for the menu validation and progress affordance) lives on
`Tab`, window scope stays with `BrowserState`, per the state model.

```
User trigger (File menu / shortcut)
        │
BrowserState.saveForLater(tab:)          Sources/States/BrowserState+SaveForLater.swift
        │
SaveForLaterService.save(tab:)           classify URL → article | video
        │
        ├── article: ReaderExtensionBridge.extractArticle(markdown: true)
        │            └─ fallback: AX-tree extraction → minimal Swift markdown
        ├── video:   APIClient → phi-agent POST /api/video-gist → markdown text
        │
        ├── always:  ReaderExportService.captureOriginalPage(tab:) → MHTML
        │
        └── SaveForLaterWriter: frontmatter + basename + collision → two files
```

A save runs as a detached task: the service captures from the tab
immediately, then owns the job to completion regardless of tab or window
lifetime. The basename is computed and reserved **once, at job start**, so
the pair can never diverge under collision handling. Article saves write
both files when their legs settle. Video saves write the MHTML and a
placeholder markdown (frontmatter + original-video link + "generating…"
note) immediately, and replace the placeholder body when the gist returns —
so the folder always shows the save, and a crash mid-gist leaves a usable
stub rather than nothing. While a job is in flight for a tab, the menu item
is disabled and further auto-triggers for it are dropped. Completion and
failure surface through the existing `OverlayToastCenter`, targeted at the
originating window when it still exists.

| Concern | Home |
| --- | --- |
| Orchestration, URL classification, fallback policy | Swift `States` |
| HTML→markdown conversion | Mirage extension (Turndown) |
| Video→article generation | phi-ai (`runVideoGist` behind a new endpoint) |
| MHTML capture | existing `ReaderExportService` (CDP) |
| Folder preference, menu, shortcut, toast | Swift `UserInterface` |
| Framework | nothing in v1 |

### Markdown comes from the extension, not from Swift

`reader.extract` already returns the sanitized, URL-absolutized article HTML
(`ExtractedArticle.contentHtml`). The conversion to markdown happens where
that HTML is produced: the Mirage reader-view background gains an
`includeMarkdown` flag on `ExtractRequest`, runs the article through
**Turndown**, and returns `contentMarkdown` alongside `contentHtml`.

Rationale:

- Turndown is already the project's HTML→markdown answer, three times over:
  the `show-current-page-as-markdown` skill (`convert.ts` — its configuration
  is the one to copy), sidecar's `extractTabAsWebpage`, and lexington. It is
  already in the shipped credits. Writing or vendoring an HTML parser plus
  converter in Swift would be a parallel implementation of an owned
  responsibility.
- The conversion input is the extension's own sanitized output, so the
  extension converting it keeps extraction and conversion in one place with
  one owner.
- Swift-side consumers (`ReaderArticle`) gain an optional `contentMarkdown`
  field; the existing HTML flow is untouched.

The accessibility-tree fallback rung never sees Turndown. Its output is
already simple, semantically flat markup (headings, paragraphs, links), so
`ReaderAccessibilityExtractor` gets a small direct markdown rendering of the
same structure. This is not a second converter — it is the stub path's better
cousin, and it handles a rung the extension cannot.

### Video saves go through a thin phi-agent endpoint

video-gist today is reachable only as an agent tool inside a chat task. A
save is not a conversation, so phi-agent gains a small authenticated
endpoint — `POST /api/video-gist` — that wraps the existing `runVideoGist`
with a fixed article-mode prompt: write the video as a markdown article,
section headings carrying timestamp deep links (`?t=…s`), attribution line
first. The Swift side calls it through `APIClient` (the networking
constraint), passing only the video URL.

Scope and limits, inherited from the capability:

- **YouTube only in v1.** The Gemini-direct route needs a public YouTube URL.
  bilibili requires the in-page caption scripts of the skill's fallback
  ladder, which only exist inside an agent task; it is deferred rather than
  half-supported. Detection mirrors `shared-types/video-urls.ts`
  (`YOUTUBE_VIDEO_URL_PATTERN` plus the video-id check) in a small Swift
  matcher; if the patterns grow they should be generated from that file
  rather than drifting by hand.
- Videos longer than ~55 minutes are rejected by the tool
  (`video_gist_video_too_long`); result text is capped at 48 KB. Both
  surface as a stub markdown with the error noted, MHTML still written.
- Generation takes tens of seconds. The save follows the background-job
  shape above: MHTML and placeholder markdown immediately, gist body on
  return. The gist call needs only the URL, so it is indifferent to the
  tab's fate.
- **Title**: the video's own title, read from the page at trigger time
  (site suffixes like " - YouTube" stripped). When the page yields no
  title, the gist supplies it — the article prompt always asks for an
  opening `# Title` heading, and Swift promotes that heading into the
  frontmatter and filename when it had none. Since the filename is
  reserved at job start, a gist-supplied title renames the pair when the
  body lands.

### Files on disk

- Basename: `YYYY-MM-DD <sanitized title>`, reusing
  `ReaderExportService.suggestedFileName`'s sanitation (promoted to a shared
  helper rather than duplicated). Collisions append ` 2`, ` 3`, …
  No dedup by URL in v1 — saving the same page twice is two snapshots, which
  is the honest behavior for a page that changes.
- Markdown frontmatter:

  ```yaml
  ---
  title: How to Do Great Work
  source: https://example.com/great-work
  saved: 2026-08-31T14:02:11Z
  site: example.com
  byline: Paul Graham
  type: article        # or: video
  trigger: manual      # or: youtube-like, x-bookmark, reddit-save, …
  ---
  ```

  A video file's body opens with `**Original video:** [title](url)` before
  the generated article.

### Settings

A new `PhiPreferences.SaveForLater` namespace with these settings:

- The **global** destination folder path (plain string — the app is not
  sandboxed, so no bookmark dance). Default `~/Documents/Phi Saved`,
  created on first save. Set in the General pane.
- An optional **per-profile override** folder, set in the profile's detail
  settings beside the download-location row (the same `NSOpenPanel`
  picker). Stored Swift-side in UserDefaults keyed by profile id — this is
  a client concept, not a Chromium pref. Effective folder =
  profile override ?? global. The override row shows "Same as global"
  until one is chosen, with a clear control to return to it.
- The site-action auto-save toggle, default off. The row is shown only
  while the `save-for-later-auto-trigger` PostHog flag is on (see Guards).

Registered in `UserDefaultsRegistration`, surfaced using the
download-location pattern from `ProfileDetailSettingsView` (`NSOpenPanel`,
`canChooseDirectories`, optimistic update) and a plain `@AppStorage`
toggle.

### Entry points

- File menu item **Save for Later**, validated like the reader toggle
  (enabled for http(s) tabs with live web contents).
- A `PHI_SAVE_FOR_LATER` shortcut constant in `Shortcuts.swift`; proposed
  default ⌥⌘S (⌘S remains Chromium's save-page; ⇧⌘S is taken by
  convention for Save As).
- Completion feedback: toast with the title and a "Show in Finder" action;
  failure toast names which half failed.
- **Site-action auto-save** — clicking a site's own save/like/bookmark
  control triggers a save (next section).
- Deferred: Chromium context-menu entry (bridge method + framework rebuild,
  the `OpenReaderView` pattern) and an address-bar affordance.

### Auto-save from site actions

Liking a YouTube video, bookmarking a post on X, saving a Reddit thread, or
bookmarking a Stack Overflow question is the user already saying "keep
this". When enabled, those clicks trigger Save for Later automatically, so
the local library accumulates without a second gesture.

**Detection lives in the Mirage content script.** Mirage already injects on
every http(s) page for the reader probe; the same script gains a
capture-phase click listener that is armed only on hosts with a trigger
rule. A hit walks `event.target.closest(selector)`, confirms the control is
transitioning **to** the engaged state (`aria-pressed`, site-specific class)
so un-liking never fires, then sends `saveForLater.trigger {url, action}`
over the existing extension messaging channel. Swift routes it through
`ExtensionMessageRouter` into the same `SaveForLaterService.save(tab:)`
path as the menu item. No new transport, and still nothing across the
Chromium bridge.

**Button selectors are data, not code.** Site markup churns; hardcoded
selectors would rot on the release train — the exact failure the reader's
site-rule corpus was built to avoid. Trigger rules use the same shape and
the same pipeline: a JSON corpus per host, bundled as a baseline in Mirage
and refreshed from the published `phi-reader-rules` manifest (a `triggers`
section beside the extraction rules). A rule is:

```json
{
  "host": "youtube.com",
  "buttons": [
    { "selector": "like-button-view-model button",
      "action": "like", "context": "page" }
  ]
}
```

Launch corpus: YouTube (like, save-to-playlist), X (bookmark, like),
Reddit (save, upvote), Stack Overflow (bookmark), and the assistants —
Gemini, ChatGPT and Claude (thumbs-up on a response), where the page a
conversation is showing is the thing worth keeping. Exact selectors are
rule authoring, not design.

**`context` matters more than the selector.** On a YouTube watch page or a
Stack Overflow question, the button belongs to the page itself — the tab is
already showing what to capture, so the normal pipeline runs as-is. On X
and Reddit the button usually sits on an item inside a feed: the thing to
save is the tweet/post **permalink**, not the timeline, and an MHTML of the
feed would be wrong. Item-context rules therefore carry an `itemLink`
selector to resolve the permalink from the button's DOM neighborhood, and
the capture must happen off the visible tab — loading the permalink in a
hidden background tab (the agent-Space pattern), extracting and capturing
there, then closing it. That background-capture machinery is real work, so:

- v1 ships **page-context triggers only** (YouTube watch, Stack Overflow
  questions, Reddit post pages, X tweet detail pages).
- Feed-item triggers ship when background capture does; until then a feed
  click writes nothing rather than saving the wrong page.

**Guards.**

- **Feature flag above the user setting.** The auto-trigger machinery is
  gated by a PostHog boolean flag (key `save-for-later-auto-trigger`),
  evaluated through `ExperimentConfigProvider` like the existing
  experiments. Effective state is `flag && user opt-in`. Swift is the
  single authority: it evaluates the flag, arms or disarms the Mirage
  click detection over the extension channel, and — defense in depth —
  drops any `saveForLater.trigger` message that arrives while disabled.
  Flag off hides the settings row entirely. This is the kill switch for
  the failure this feature is uniquely exposed to: a site markup change
  making a rule misfire and spray files to disk, remotely stoppable
  without waiting on a rules-corpus refresh or an app release. Manual
  saves are not behind the flag.
- Opt-in: a single toggle, default **off**. Auto-writing files to disk on a
  like is delightful when asked for and alarming when not.
- Transition detection plus a short in-memory recent-URL window (~10
  minutes) prevents double saves from repeated toggling; beyond the window
  a re-trigger is a fresh snapshot, consistent with manual saves.
- The auto-save toast carries **Undo**, which trashes the just-written pair
  — an automatic action needs a cheaper exit than Finder. Undo also
  cancels the job's pending work (a video save's in-flight gist write), so
  a file cannot reappear after the user removed it.
- Everything is local: click detection runs in the page, rules are static
  data, and no engagement signal leaves the machine.
- Frontmatter records provenance: `trigger: manual | youtube-like |
  x-bookmark | reddit-save | …`.

## Failure Matrix

| Condition | Markdown | MHTML |
| --- | --- | --- |
| Normal article | extension ladder → Turndown | captured |
| Extraction refuses, AX available | AX rung → Swift rendering | captured |
| Extraction and AX both refuse | stub (frontmatter + link + note) | captured |
| Extension unavailable | AX rung or stub | captured |
| YouTube video, signed in | video-gist article | captured |
| YouTube video, signed out / AI off | stub with link | captured |
| Video too long / gist error | stub with link + error note | captured |
| Non-YouTube video site | treated as article (ladder output) | captured |
| CDP capture fails | written normally | error toast, save still counts |
| Tab closes mid-capture | legs already captured are written; the rest degrade (stub / noted as missing) | same |
| Tab closes after capture | unaffected — the job is detached | unaffected |
| Destination folder missing/unwritable | error toast, nothing written, settings opened |  |

## Phases

**Phase 1 — Article saves.**
Mirage: `includeMarkdown` on `reader.extract`, Turndown dependency, config
copied from `show-current-page-as-markdown`. Swift: `SaveForLaterService`
with the background-job shape, writer, `SaveForLater` preferences (global
folder + per-profile override), File menu item + shortcut, toast via
`OverlayToastCenter`, AX fallback rendering, stub path, guest-mode
disable. All new strings follow the localization guidelines. Ships useful
on its own.

**Phase 2 — Video saves.**
phi-ai: `POST /api/video-gist` endpoint wrapping `runVideoGist` with the
article prompt — remaining contract work: request/response schema, stable
error codes surfaced to Swift, honoring the existing `VIDEO_GIST_ENABLED`
kill switch, and a per-user quota decision (each save is a Gemini call).
Swift: URL classification, `APIClient` call, placeholder-then-replace
write, title promotion/rename, video frontmatter/body shape.

**Phase 3 — Site-action auto-save (page context).**
Mirage: trigger-rule corpus + click detection + `saveForLater.trigger`
message; rules published beside the extraction rules. Swift: router route,
`save-for-later-auto-trigger` PostHog flag, opt-in toggle, dedup window,
Undo toast. Page-context sites only.

**Phase 4 — Reach.**
Feed-item triggers via hidden background-tab capture (X/Reddit timelines);
Chromium context-menu entry (one bridge method, `OpenReaderView` pattern);
address-bar affordance; bilibili via the caption-script route; optional
saved-items browsing surface reading the folder.

## Non-Goals

- No sync, no tagging, no database, no in-browser library UI (v1).
- No video file downloads, ever.
- No per-item asset mirroring (the MHTML is the offline copy).
- No PDF saves (the reader declines PDFs; a PDF is already a file — deferred
  until the reader's PDF phase lands).

## Open Questions

1. Default folder (`~/Documents/Phi Saved`) vs. forcing a first-save picker.
2. Whether the webpage version should be skippable per save (a modifier on
   the menu item) or always-on. Always-on is recommended for predictability.
3. Shortcut choice (⌥⌘S proposed; ⌥⌘R precedent from the reader).
4. Whether video saves should also attach the raw transcript when the gist
   falls back — deferred with bilibili, since both need the script ladder.
5. Which site actions arm the auto-save: "save/bookmark" actions are
   unambiguous intent; "like/upvote" is broader. Recommended: both armed by
   the single toggle at launch, split into per-action choice only if real
   use shows likes are too noisy.

## Resolved

- Flat file pair (decided 2026-08-31): each save is `<basename>.md` +
  `<basename>.mhtml` directly in the destination folder, no per-item
  subfolder.
- Video markdown title (decided 2026-08-31): the video's own title;
  when the page yields none, the gist article's opening heading.
- Folder scope (decided 2026-08-31): the user chooses — a global default
  folder plus an optional per-profile override.
- Background saves (decided 2026-08-31): a save is a detached job;
  closing the tab mid-save does not affect it.
